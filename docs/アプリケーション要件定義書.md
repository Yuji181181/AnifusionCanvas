# **アプリケーション開発用詳細要件定義書**

## **開発の背景と目的**

アニメーション制作産業は世界的な需要の拡大を背景に成長を続けているが、その制作現場は歴史的に極めて労働集約的なプロセスに依存している。特に、原画と原画の間を補間して滑らかな動きを作り出す「中割り」の工程は、膨大な作画枚数を必要とし、制作スケジュールの遅延やクリエイターの過重労働を引き起こす最大のボトルネックとなっている。

これまでの映像制作業界では、実写映像向けのフレーム補間技術を用いた自動化が試みられてきたが、アニメーションのフレームは時間的に疎（Sparse）であり、非線形な大きな動きや隠蔽（オクルージョン）を伴うため、従来技術では不自然な破綻が必然的に生じていた。

本プロジェクトは、これらの課題を解決する「アニメ制作DX」を実現するためのプロトタイプ（デモ）開発である。最新の生成AI技術とモダンなWebフロントエンド技術を統合した「Human-in-the-Loop（人間とAIの協調）」のワークフローを構築し、現場のクリエイターが実務で利用可能なレベルの支援ツールを提案する。

また、本デモアプリケーションの開発は、エンターテインメントの基盤と高度な技術力を併せ持つ企業に対する、開発者の強い熱意とフルスタックなAIエンジニアリング能力をアピールするためのポートフォリオとして機能することを最大の目的としている。

## **推奨OSS選定とアーキテクチャ**

個人開発において、全ての機能を一から実装することは非現実的である。本プロジェクトでは、各機能領域で最適なOSSを選定し、それらを適切に組み合わせることで、短い開発期間でも高品質なアプリケーションを実現する。

### **フロントエンド構成**

| 機能領域 | 推奨OSS | 選定理由 |
|---------|---------|----------|
| **アプリケーション基盤** | **Vite+ + React** | SSRを行わない完全なSPAとして構築し、軽量な開発体験と高速なビルドを両立できる |
| **ルーティング** | **TanStack Router** | 型安全なルーティング定義が可能で、SPAに適した画面遷移設計を行いやすい |
| **UIコンポーネント** | **shadcn/ui + Radix UI** | アクセシビリティ対応済み、TailwindCSSとの親和性、カスタマイズ性が高い |
| **状態管理** | **Zustand** | シンプルなAPI、TypeScriptネイティブ、小規模〜中規模に最適 |
| **データフェッチ** | **TanStack Query** | API通信、キャッシュ、再取得、ポーリング、ミューテーション管理を統一的に扱える |
| **フォーム管理** | **React Hook Form + Zod** | パフォーマンス優秀、型安全性あり |
| **品質管理** | **Oxlint + Oxfmt** | Vite+標準の品質管理ツール群として導入しやすく、高速に静的解析と整形を実行できる |

### **バックエンド構成**

| 機能領域 | 推奨OSS | 選定理由 |
|---------|---------|----------|
| **言語・実行環境** | **Go** | 単一バイナリでデプロイしやすく、Cloud Run上での運用とFFmpeg同梱に適している |
| **Webフレームワーク** | **Echo** | 軽量で高速、REST APIの実装に向いており、ミドルウェア構成も明快 |
| **DBアクセス** | **sqlc + go-sql-driver/mysql** | TiDB（MySQL互換）に対して型安全かつ明示的なSQLベースの実装ができる |
| **マイグレーション** | **golang-migrate** | スキーマ変更をGoプロジェクトの運用フローに組み込みやすい |
| **非同期処理** | **Goroutine + Channel** | Replicate APIのポーリングやジョブ状態管理をGo標準機能でシンプルに構成できる |
| **動画処理** | **FFmpeg + os/exec** | ToonCrafterの動画出力分割と最終MP4書き出しを柔軟に制御できる |
| **オブジェクトストレージ連携** | **AWS SDK for Go v2** | Cloudflare R2とS3互換APIで安定して連携できる |
| **デプロイメント** | **Docker + Google Cloud Run** | ゼロスケールとHTTP API運用を両立しつつ、FFmpeg実行環境をコンテナに閉じ込められる |

### **Canvas編集とAI機能の分離**

本アプリケーションの最大の設計上の判断は、**Canvas編集機能とAI推論機能を明確に分離すること**である。

**Fabric.jsの役割（純粋なCanvas編集）:**
- ステップ3「手動編集」でのみ使用
- 機能: ペン描画、図形、フィルター、ピクセル単位編集
- Fabric.jsにAI推論ロジックを混在させない

**shadcn/ui + カスタム実装（AIワークフローUI）:**
- ステップ1「AI中割り生成」: フォームUI、プレビュー
- ステップ2「Inpainting編集」: マスク描画用Canvas（Fabric.jsの最小機能）+ プロンプト入力フォーム

### **テスト戦略**

品質担保のため、以下のテストアプローチを採用する：

**単体・統合テスト: Vitest**
- フロントエンドのユニットテストフレームワークとして **Vitest** を採用
- ESMネイティブ、TypeScriptサポートが優秀
- Reactコンポーネント、カスタムフック、ユーティリティ関数のテスト
- TanStack Queryを用いたAPI通信部分のモックテスト

**E2Eテスト: Playwright**
- **Playwright** をE2Eテストフレームワークとして採用
- Chromium, Firefox, WebKitのマルチブラウザサポート
- 主要ユーザージャーニーの自動化:
  - 中割り生成 → Inpainting編集 → 手動編集 → 動画書き出し
- ヘッドレス実行でのCI/CD統合

**バックエンド結合テスト: Go testing + testcontainers-go**
- バックエンドはGo標準の **testing** パッケージを使用する
- **testcontainers-go** を組み合わせ、TiDB互換のDB接続や周辺依存を含む結合テストを実施する
- リポジトリ層、APIハンドラ、ジョブ制御、FFmpeg実行の周辺処理を実運用に近い形で検証する

**テスト実装方針**
- ビジュアルリグレッションテストはスコープ外（ポートフォリオ用途のデモのため）
- 重要なビジネスロジック（フレーム管理、API通信、ジョブ状態遷移）は単体テストと結合テストでカバー
- クリティカルパス（3ステップのワークフロー）はE2Eテストで保証

## **システムアーキテクチャおよび技術スタック**

本アプリケーションは、運用コストの最適化とデモとしての軽快な動作を両立するため、フロントエンドとバックエンドの責務を完全に分離したアーキテクチャを採用する。以下の技術スタックを厳守して実装すること。

| コンポーネント / 領域 | 指定技術および制約 |
| :---- | :---- |
| **フロントエンド基盤** | **Vite+ + React** を採用し、SSRを行わない完全な **SPA** として構築する。実行環境およびパッケージマネージャーには **bun** を使用すること。 |
| **フロントエンド配信** | フロントエンドは静的アセットとしてビルドし、**Cloudflare Pages** にデプロイする。 |
| **ルーティング** | **TanStack Router** を使用し、ステップ別画面遷移とURL設計を明確に管理する。 |
| **データフェッチ・通信** | バックエンドのGo APIサーバーへ直接通信を行い、データ取得、ミューテーション、ジョブ状態監視、APIポーリングには **TanStack Query** を使用する。 |
| **スタイリング** | **TailwindCSS** を使用してモダンでレスポンシブなUIを構築する。 |
| **バリデーション** | **Zod** を使用し、フロントエンドの入力検証およびAPIのリクエスト/レスポンスの型安全性を担保する。 |
| **コード品質管理** | リンターおよびフォーマッタとして **Oxlint** と **Oxfmt** を採用する。 |
| **状態管理** | **Zustand** を使用してフレーム管理などのグローバル状態を管理する。 |
| **画像編集・UI** | **Fabric.js** を用いてキャンバスを実装し、ステップ2（マスク描画）とステップ3（フル機能編集）で使用する。 |
| **バックエンド・API基盤** | **Go + Echo** を使用する。データベースとの接続、ジョブ管理、外部ストレージ連携、Replicate API連携、FFmpeg実行などのビジネスロジックはすべてGo側に集約する。 |
| **バックエンド配備** | バックエンドは **Dockerコンテナ** として構築し、**Google Cloud Run** 上で稼働させる。ゼロスケール運用と **FFmpeg** 実行環境の両立を前提とする。 |
| **DBアクセス** | **TiDB Serverless** に対する操作は **sqlc** と **golang-migrate** を使用して実装し、ドライバには **go-sql-driver/mysql** を採用する。 |
| **非同期処理** | Go標準の **Goroutine と Channel** を用いてReplicate APIのポーリング、ジョブ状態遷移、書き出し処理の並行制御を行う。 |
| **オブジェクトストレージ** | **Cloudflare R2**。アップロード・ダウンロード・オブジェクト操作には **AWS SDK for Go v2** を使用する。 |
| **データベース** | **TiDB Serverless** を使用し、フレーム、ジョブ、プロジェクト等のメタデータを管理する。 |
| **GPU推論基盤** | **Replicate API** を使用し、AI推論をWeb API経由で実行する。自前でのGPUインフラ構築・運用は行わず、Replicateのホスト型推論サービスを利用することで、デモ開発の迅速化と運用コストの最小化を図る。 |
| **動画処理** | Go標準の **os/exec** パッケージ経由で **FFmpeg** を呼び出し、フレーム分割およびMP4エンコードを行う。 |
| **フロントエンドテスト** | **Vitest** - Reactコンポーネント、カスタムフック、ユーティリティ関数、TanStack Query連携のテスト。 |
| **E2Eテスト** | **Playwright** - ユーザージャーニーの自動化、マルチブラウザサポート（Chromium, Firefox, WebKit）。 |
| **バックエンドテスト** | **testing + testcontainers-go** - Echoハンドラ、サービス、DB連携、ジョブ制御の結合テスト。 |

### **ディレクトリ構成**

本プロジェクトのディレクトリ構成は、**デプロイ単位（web / api）を最上位で分離しつつ、その中では機能単位で責務を閉じる** 方針で設計する。フロントエンドは「route起点 + feature単位」、バックエンドは「entrypoint起点 + internal配下のレイヤ分離」を基本とし、共有契約・インフラ・ドキュメントはアプリケーション本体から独立させる。

## **インタラクティブな編集ワークフロー（UI要件）**

本アプリケーションのコアとなるユーザー体験は、AIにすべてを任せるのではなく、クリエイターが介在してクオリティを担保する以下の3ステップのフローで構成される。フロントエンドはこのフローを直感的に操作できるSPAを提供すること。

### **ステップ1: AIで中割りを生成**

ユーザーが2枚の原画（キーフレーム）をアップロードし、生成したい枚数を指定すると、バックエンドのAIがその間のフレームを自動補間し、個別のフレーム画像としてタイムラインに並べる。

**使用技術:**
- UI: shadcn/ui（フォーム、ボタン、アップロード）
- 画面遷移: TanStack Router
- 状態管理: Zustand（アップロード進捗、生成ジョブ状態）
- 通信: TanStack Query（Go APIへのミューテーションとポーリング）
- 表示: 生成されたフレームをタイムラインコンポーネントで表示

### **ステップ2: AIで、その生成した画像に対して自然言語で指示をして修正**

生成された中割り画像の中で破綻している部分（例：手の形がおかしい等）があった場合、ユーザーはエディタのキャンバス上でそのフレームだけをブラシでマスク（黒塗り）する。その後、「握りこぶし」などの自然言語によるプロンプトを入力して再生成を指示することで、AIがそのマスク部分だけを修正（Inpainting）する。

**使用技術:**
- マスク描画: Fabric.js（ブラシ機能のみ使用、最小限の実装）
- プロンプト入力: shadcn/ui（テキストエリア、ボタン）
- 通信: TanStack Query（マスク画像とプロンプトをGo APIへ送信し、結果をポーリング）
- 状態管理: Zustand（編集中のフレーム状態）

**Fabric.jsの使用範囲（最小限）:**
```javascript
// マスク描画のみに限定
const maskCanvas = new fabric.Canvas('maskCanvas', {
  isDrawingMode: true,
  width: 512,
  height: 512,
});
maskCanvas.freeDrawingBrush = new fabric.PencilBrush(maskCanvas);
maskCanvas.freeDrawingBrush.color = 'black';
maskCanvas.freeDrawingBrush.width = 20;
```

### **ステップ3: それでも修正できなかった部分を、人間の手で直接編集**

AIの自然言語修正でもクリエイターの意図に完璧に合致しない1ピクセル単位のズレや色の修正については、キャンバスエディタ上の描画ツールを用いて、人間の手で直接ピクセルを編集・加筆して最終的な完成とする。

**使用技術:**
- キャンバスエディタ: Fabric.js（フル機能）
- 機能一覧:
  - ペンツール（自由描画、線の太さ・色変更）
  - 図形ツール（四角、円、多角形）
  - テキストツール
  - 画像フィルター（明度、コントラスト、彩度、ブラー）
  - 選択・変形（移動、回転、スケール）
  - レイヤー管理（重ね順、表示/非表示）
  - アンドゥ/リドゥ

**Fabric.jsのフル活用:**
```javascript
const editorCanvas = new fabric.Canvas('editorCanvas', {
  width: 1024,
  height: 1024,
  backgroundColor: '#f0f0f0',
});

// 画像読み込み
fabric.Image.fromURL(frameImageUrl, (img) => {
  editorCanvas.add(img);
  editorCanvas.renderAll();
});

// フィルター適用
const applyFilter = (filterType, value) => {
  const activeObject = editorCanvas.getActiveObject();
  if (activeObject && activeObject.type === 'image') {
    activeObject.filters.push(new fabric.Image.filters[filterType]({ value }));
    activeObject.applyFilters();
    editorCanvas.renderAll();
  }
};
```

### **ステップ4: 動画化は最後に手動で実行**

細部の修正が終わったあと、ユーザーが明示的に書き出しボタンを押した場合のみ、フレーム列をFFmpegでMP4に結合する。自動再生用のプレビュー生成と、最終書き出しは分離する。

**使用技術:**
- プレビュー: HTML5 Video要素（フレーム画像を順番に表示する簡易プレビュー）
- 書き出し: Go API経由でFFmpeg実行
- 通信: TanStack Query（書き出しジョブのポーリング）

## **AIモデルの選定と推論要件**

デモの品質と実装の現実性を両立するため、AI推論パイプラインは **Replicate API** を利用したホスト型推論サービスとして構築する。自前でのGPUインフラ構築・モデルのデプロイ・運用は行わず、Replicate上で公開されている既存モデルのAPIを呼び出すことで、開発の迅速化と運用コストの最小化を図る。

* **中割り生成モデル:** アニメーションのフレーム補間に特化した **ToonCrafter** を、Replicate上の `fofr/tooncrafter` API経由で利用する。
  * **入力:** image_1（1枚目の原画）、image_2（2枚目の原画）、prompt（動作のテキスト描述）、negative_prompt、max_width/height 等
  * **出力:** MP4動画（URI）。バックエンド側でFFmpegを用いて個別PNGフレームに分割し、R2にアップロードしてフレーム画像として管理する。
  * **料金:** $0.0014/秒（A100 80GB）。中央値約$0.064/回（1回約46秒）。
* **部分修正（Inpainting）モデル:** ステップ2の自然言語による修正機能には、Replicate上の `lucataco/sdxl-inpainting` API（Stable Diffusion XL Inpainting）を利用する。
  * **入力:** image（入力画像）、mask（マスク画像）、prompt（生成内容のテキスト描述）、negative_prompt、strength、steps 等
  * **出力:** 修飾画像のURL（PNG）。
  * **料金:** $0.000975/秒（L40S）。中央値約$0.0026/回（1回約2.7秒）。
* **1セッションあたりの概算コスト:** ToonCrafter 1回（$0.064）＋ Inpainting 2〜3回（$0.005〜0.008）＝ **約$0.07/セッション（約7円）**

* **キャラクター制御（LoRA適用）:** 別のタスクとして事前学習済みのキャラクターLoRAモデルが用意される想定である。推論時にこのLoRAの重みをベースモデルに適用し、キャラクターのアイデンティティを保った画像を生成できるように実装すること。
* **IP-Adapter（オプション）:** ユーザーが設定画（リファレンス画像）をアップロードし、その画像特徴量をプロンプトとして直接モデルに注入する機構の導入も推奨する。

## **バックエンド推論処理と非同期ジョブ制御の要件**

長時間を要するAI推論ワークロードを安定して処理するため、Go（Echo）バックエンドとSPAフロントエンドの間で適切な非同期通信パターンを構築する。

* **ジョブ受付とポーリング:**
  フロントエンドからGo APIへ推論をリクエストした際、APIは即座にジョブIDのみを返却し、内部では **Goroutine** を起動してReplicate APIの呼び出しと進行管理を開始する。ジョブの状態監視や結果取得は **Channel** を用いた内部連携で整理し、フロントエンドは **TanStack Query** による定期ポーリングでジョブの完了ステータスと生成された画像のURLを取得する構成とすること。
* **ToonCrafter出力のフレーム分割:**
  ToonCrafter APIはMP4動画を出力するため、バックエンド側で **os/exec** 経由でFFmpegを呼び出し、個別PNGフレームに分割する。分割した各フレーム画像をCloudflare R2にアップロードし、フレームごとのURLをDBに保存することで、タイムライン上で個別フレームとして表示・編集可能にする。
* **動画のエンコーディング (FFmpeg):**
  生成された複数枚のフレームは、まず個別画像として保持する。フレームの細かい編集が終わったあと、ユーザーが手動で書き出しを押した時だけMP4動画として結合する。本アプリケーションはポートフォリオ用のデモであるため、厳密な24fpsや30fpsにこだわる必要はない。ToonCrafterの出力仕様や実装の容易さを最優先とし、最も実装が簡単でエラーが起きにくいフレームレートを実装担当AIが選択してFFmpegのエンコード設定を行うこと。
* **ジョブ管理の実装要件:**
  ジョブ状態（queued / running / succeeded / failed）をTiDBで管理し、Goroutineの暴走や二重実行を防ぐため、ジョブごとの状態遷移と排他をサービス層で明示的に制御すること。Replicate APIのポーリング、FFmpeg実行、R2アップロードは責務ごとに分離し、Channelまたはコンテキストを用いてキャンセルやタイムアウトを伝播できる設計とする。
* **Cloud Run前提の実行設計:**
  バックエンドはGoogle Cloud Run上のコンテナで稼働するため、インスタンスのスケールアウト/スケールインを前提に、ジョブの永続状態はアプリケーションメモリではなくTiDBに保持すること。FFmpeg実行に必要なバイナリや依存はDockerイメージに含め、ゼロスケール復帰後でも同一手順で処理を再開できる構成とする。

実装の細部（DBスキーマやAPI仕様など）は本要件定義書の意図を汲み取り、実装を担当するAIエージェントが最も効率的で堅牢な設計を自ら考え、コードとして具現化すること。
